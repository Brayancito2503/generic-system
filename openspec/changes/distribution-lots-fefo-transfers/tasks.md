## Migration ledger

Six additive migrations except M6, ordered, each hand-applied over `DIRECT_URL` and replicated into `prisma/migrations/<ts>_*/migration.sql` (read-only pattern reference: `prisma/migrations/20260925120000_velocity_sort_index/migration.sql`). Prisma cannot express a partial unique index, so M5 and M2's implicit-lot index ship as hand-written SQL — the same pattern already in the repo.

| # | Slice | DDL | Reversal | Gate |
|---|---|---|---|---|
| **M5** | S1b | `CREATE UNIQUE INDEX "CashSession_one_open_per_branch" ON "CashSession"("tenantId","branchId") WHERE "status"='OPEN'` | `DROP INDEX` | Pre-check: no `(tenantId,branchId)` with 2+ OPEN rows (impossible under today's tenant-wide guard, possible in hand-edited data). Safe **before** the code lands — it enforces strictly less than today's app guard. |
| **M1** | S2a | `CREATE TABLE "ItemBranchCost"` + seed | `DROP TABLE "ItemBranchCost"` | No duplicates on `(tenantId,itemId,branchId)`; then every `Inventory` pair has exactly one row whose `cost` = the current `Item.cost`. |
| **M2** | S3a | `CREATE TYPE "LotStatus"`; `CREATE TABLE "Lot"`; `CREATE UNIQUE INDEX "Lot_one_implicit_per_item_branch" ON "Lot"("tenantId","itemId","branchId") WHERE "code" IS NULL`; `INSERT` one implicit lot per `Inventory` row (`quantity = stock`, `cost = Item.cost`, `code`/`expiryDate` NULL) | `DROP TABLE "Lot"; DROP TYPE "LotStatus";` | **G2.** The `@@unique([tenantId,itemId,branchId,code])` does **not** enforce the implicit-lot rule: Postgres treats NULLs as distinct, so two `code = null` lots would both be allowed. The partial index is mandatory, not a nicety. |
| **M3** | S4b | `ADD COLUMN "InventoryMovement"."lotId"/"lotCode"`; FK **explicitly** `ON DELETE RESTRICT`; `CREATE INDEX`; `CREATE TABLE "SaleItemLot"` | drop table, constraint, index, columns | Prisma defaults an *optional* relation to `SetNull`; `SetNull` would silently rewrite history instead of refusing, so `Restrict` must be written explicitly. |
| **M4** | S7a | `CREATE TYPE "StockTransferStatus"`; `CREATE TABLE "StockTransfer"`, `"StockTransferItem"` | drop both tables + type | Both lot FKs `RESTRICT`. |
| **M6** | S5c | `ALTER TABLE "Inventory" DROP COLUMN "stock"` | `ADD COLUMN "stock" numeric(10,2) NOT NULL DEFAULT 0` + `UPDATE … FROM (SELECT … SUM(quantity) … GROUP BY 1,2,3)` | **Only safe trigger:** the M2(a) reconciliation returns 0 mismatches **at the moment of the drop**. Deliberately separated from S5b so a failed gate defers only the drop. |

**Ordering rationale.** M5 first (the only index safe before its code lands). M1 before M2 (branch cost must exist before a lot carries cost). M6 last and alone (the only non-additive step). **[A1] Adding D11 introduces no new DDL** — M5's index is simultaneously the uniqueness constraint *and* the access path for the derived-branch lookup, and the derivation chain rides `User.id` (PK) plus the two `@unique` columns `User.personId` and `Employee.personId`. S1c applies no DDL at all.
